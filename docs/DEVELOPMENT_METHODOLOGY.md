# Development Methodology and Contributions

## AI-assisted reverse engineering plus human runtime validation

This project used a collaborative workflow with two distinct and indispensable roles.

### ChatGPT/Codex (OpenAI)

ChatGPT/Codex produced the project-authored technical work: static analysis of listings and runtime disassembly; layered Action/motion/state/Guard/recoil/collision models; causal and control experiments; GDB preflight/install/status/restore scripts; bounded guest loggers and export tools; ARM hooks, wrappers, caves, builders, and validators; regional relocation support; and documentation drafts.

It did not operate Azahar, connect directly to the live game process, press game inputs, or directly observe the final animations and monster contacts.

### JackUnderTheHood

JackUnderTheHood maintained the actual game, emulator, debugger, disassembler, and file environment; ran every debugger command and project script; collected runtime logs, memory, register state, and machine-code readback; performed gameplay tests; classified valid and contaminated samples; identified visible failures; chose project direction; accepted or rejected candidates; and completed final runtime acceptance and publication.

## Why AI output is not runtime evidence

Static analysis can show how a branch is encoded or that a function can read a field. It cannot by itself prove that a hook executes in the target build, ExeFS loads before JIT compilation, an animation remains clean, an attack is actually blocked, a burst occurs only once, or state is recovered after the action.

Important candidates therefore required proportional validation: original-instruction and zero-cave preflight, full installation readback, minimal no-contact smoke, positive and negative gameplay controls, final state inspection, safe restoration, cold-start ExeFS/JIT acceptance, deterministic builds, and archive checksums.

## Azahar/GDB constraints

Azahar 2126.0 was the first sufficiently stable dynamic-research baseline. Earlier versions could not maintain the required remote connection. Conventional breakpoints and watchpoints remained too fragile for primary collection even on 2126.0, so fixed-address status scripts, temporary code hooks, Action-filtered bounded loggers, chunked memory export, offline analysis, readback, and restoration became the main workflow.

## Handling failed experiments

- A crash caused by a builder or wrapper error is an engineering failure, not game-mechanism evidence.
- Samples contaminated by a wrong cheat, stale IPS, save state, or still-enabled experiment are discarded.
- A one-off phenomenon remains an observation until it is independently reproduced.
- A zero log becomes branch-bypass evidence only when the same installation contains a reliable positive control.
- Withdrawn candidates remain archived with explicit labels and must not be cited as formal releases.

## External material

Publicly shared MH4U Charge Blade Gateshark material from Hazerou provided an important early lead and helped identify separate input branches. It is credited as external material, not described as project-authored code. The project independently recorded Actions, located functions, relocated hooks, and tested each supported build. No Hazerou code or assets are included in the releases.
