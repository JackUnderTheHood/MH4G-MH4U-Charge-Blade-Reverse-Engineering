# MH4G / MH4U Charge Blade Project — Development Methodology and Contribution Disclosure

[中文版本](DEVELOPMENT_METHODOLOGY.zh-CN.md)

## AI-assisted reverse engineering with human runtime validation

This project used a collaborative workflow: **AI-assisted reverse engineering and implementation, combined with human-operated dynamic experiments and gameplay validation**. It should not be described either as “made entirely by AI” or as reverse engineering performed entirely by one person without AI assistance.

### ChatGPT / Codex (OpenAI)

ChatGPT and Codex performed the project’s code-analysis and implementation work. Their contributions included:

- analyzing the MH4G / MH4U disassembly, runtime dumps, memory readbacks, logs, screenshots, and test reports supplied during the project;
- building the layered Action → entry parameters → motion/phase → resource lifetime → Guard/collision model;
- proposing mechanism hypotheses, controlled comparisons, failure criteria, and safe experiment sequences;
- designing the GDB preflight/enable/status/disable workflow, temporary hooks, bounded loggers, memory-export procedures, and readback checks;
- producing the project-authored reverse-engineering scripts, ARM hook/overlay machine-code designs, IPS builders, validators, and release-packaging logic;
- decoding branches, relocating the implementation for MH4U USA/EUR, checking code caves and IPS records, and interpreting returned data;
- drafting and organizing the public README, Technical Analysis, Research History, Porting Notes, release metadata, and archive structure.

In short, the project-authored reverse-engineering code and patch implementation were generated by ChatGPT/Codex as part of the collaboration. The AI did not independently operate Azahar, connect to the live game process, press gameplay inputs, or directly witness the resulting animation and combat behavior.

### Project author and test operator

The project author performed the runtime research and empirical acceptance work. Their contributions included:

- providing and maintaining the actual MH4G / MH4U, Azahar, GDB, Ghidra, and local-file environment;
- bringing practical Charge Blade knowledge and identifying the intended gameplay behavior and useful comparison cases;
- running every GDB command and project script against the live emulator process;
- installing, enabling, disabling, restarting, and switching experimental and ExeFS builds under the required safety conditions;
- executing the prescribed no-stick/stick-input, morph/fast-morph, red-shield, GP, consecutive-use, follow-up, rolling, and area-transition tests;
- collecting runtime dumps, memory values, logs, screenshots, hashes, and observable gameplay results, then returning those results for analysis;
- distinguishing invalid samples—such as bad facing, mistimed contact, contaminated action sequences, connection failures, or the EUR title-screen test—from valid evidence;
- comparing the finished behavior with MHGU, deciding the acceptance criteria and project scope, and performing the final JPN/USA/EUR gameplay validation.

The project’s conclusions therefore were not accepted from static AI inference alone. Major claims required agreement among script output, machine-code readback, repeatable controlled tests, and behavior observed by the human operator in the running game.

## Evidence and reproducibility boundary

AI output in this project is an analytical and implementation contribution, not a substitute for runtime evidence. A hypothesis, address mapping, branch encoding, or patch design remained provisional until it passed the project’s relevant checks. Depending on the phase, those checks included original-word preflight, full installed-code readback, safe restoration, positive and negative controls, repeatable in-game behavior, CPU-JIT-on regression, deterministic builds, and archive checksum verification.

Conversely, an isolated gameplay observation was not automatically treated as proof of a mechanism. The project repeatedly rejected or downgraded samples when the action path, contact timing, connection state, process state, or instrumentation validity could not be established.
