# 移植说明：MH4G JPN、MH4U USA 与 MH4U EUR

## 1. 可以迁移的是结构，不是地址

三个版本的 Action 语义和大量函数结构高度相似，因此已经验证的行为模型可以复用：

```text
原生 GP mask 时序
→ 防御成立与 GP 后退修正
→ 快速成功接触的红盾瓶爆条件
→ 蓄力结果分档与直接瓶爆提交
```

但每个版本的函数地址、当前玩家指针所在位置（人物根槽）、分支距离和可用空白代码区（code cave）都可能不同。移植时不能：

- 只修改 Title ID；
- 只修改文件名；
- 假设所有地址使用同一个固定偏移；
- 把一个地区的 Gateshark 地址直接复制到另一个地区。

实际映射也证明不存在一个可套用到全部函数的“地区固定偏移”。例如从日版到美版：

```text
B56160 → B6D440   +0x172E0
B05488 → B1C6A0   +0x17218
CA92A8 → CC4350   +0x1B0A8
```

三个偏移并不相同。USA 到 EUR 的这几处核心函数最后都恰好得到 `+0x50`，但这是逐个结构签名核对后的结果，不是预先假定的通用规律；人物根槽、code cave 和其他代码仍然必须独立检查。

## 3. 移植流程

### 第一步：取得目标版本自己的运行时镜像

先确认连接的是正确游戏和正确地区，再只读导出目标版本的可执行代码范围。Azahar GDB 对大块读取存在限制时，应使用已经验证的有限分块导出方式，而不是把一次失败的 `find` 当作“目标不存在”。

运行时镜像只用于本地分析，不进入发布包。

### 第二步：用结构签名定位函数

以完整指令序列、相邻控制流、调用关系和已知 Action 行为共同定位：

- GP mask helper；
- 快速成功接触写入点；
- 动作结果入口；
- 原生瓶爆提交函数；
- 当前玩家根槽。

不要只搜索一个常量或一条指令。短签名可能在无关函数中重复。

### 第三步：验证 code cave

候选 cave 必须满足：

- 容量足够；
- 运行时完整读回为零；
- 没有已知 literal 引用或分支目标进入该区域；
- 地址满足 ARM 分支范围和对齐要求；
- 安装前可以完整 preflight，卸载后可以完整清零。

### 第四步：逐条重新计算跳转

内部相对布局可以复用行为设计，但以下内容必须按目标版本重新计算：

- 每个 hook 跳到 code cave 的 ARM `B`／`BL`；
- code cave 执行完后返回原函数的位置；
- 调用原生瓶爆提交函数的带返回地址跳转；
- 人物根槽等写在补丁代码中的绝对地址（literal）；
- 条件跳转，以及用于跨越较远距离的中转跳板（veneer）。

### 第五步：先静态验证，再动态安装

构建器至少应检查：

- 覆盖指令在 wrapper 中得到重放；
- 分支反解后的目标地址正确；
- CPSR flags、保存寄存器和 LR 恢复正确；
- Action、mask、状态偏移和人物根 literal 正确；
- cave 大小、边界零区和 SHA-256 正确；
- IPS 编解码 round trip 与预期字节一致；
- 连续构建结果确定性一致。

动态阶段必须遵循：

```text
冷启动
→ 只读 preflight
→ 确认原指令和全零 cave
→ 安装
→ 逐字读回
→ 最小无接触 smoke
→ 功能矩阵
→ 最终 status
→ 安全 restore
```

## 4. 最低功能矩阵

### 快速变形斩 GP v4

- 不推动左摇杆与推动左摇杆的无接触动画；
- 两个分支在无红盾下成功 GP 且无瓶爆；
- 两个分支在红盾下成功 GP 且只产生一次瓶爆；
- 大解和斧下砸派生；
- 普通变形斩、普通 GP 和长按 R 防御回归；
- 最终 hook／cave 状态完整；
- restore 后原指令和 cave 全零。

### 合并版

除上述项目外，还应覆盖：

- 蓄力很短、适中释放和持续按住自动释放；
- 无红盾的小／中／大后退均无瓶爆；
- 红盾的小／中／大后退均产生一次瓶爆；
- 小／中后退继续蓄力；
- 大后退打断蓄力；
- 普通防御与普通变形没有被蓄力结果过滤逻辑误命中。

多段攻击目前仍是保留边界，不应在移植文档中写成已完整覆盖。

## 5. EUR 错误地区金手指案例

EUR 联合测试时曾在爬墙路径两次崩溃于 `00B96990`。最终发现同时启用的外部代码写入：

```text
00B96958 E3A00001
```

该地址来自 USA 布局。EUR 的 `00B96958` 原本是必要指令 `E58D1008`，却被错误改成了 `E3A00001`；USA 中的目标指令 `E3A01001` 在 EUR 的对应位置其实是 `00B969A8`。仅在 UI 中关闭金手指并不会撤销已经写入的代码，必须完整冷启动。

移除错误写入并冷启动后，在保持 GP 候选不变的情况下连续爬墙五次稳定，完整功能矩阵随后通过。这个案例说明：

- 运行时异常不能仅凭 PC 是否落在本项目 cave 内判断归因；
- 必须记录所有同时启用的代码修改；
- 不同地区的地址绝不能直接复用；
- 关闭 UI 选项不等于运行时机器码已经恢复。

## 6. 发布工程

每个地区、每种功能包都应拥有独立：

- 文件名；
- Title ID；
- `code.ips` SHA-256；
- code cave SHA-256；
- ZIP SHA-256；
- 中英文 README；
- manifest 与内部 `SHA256SUMS`；
- 明确的运行时测试状态。

合并版 README 必须写明已经包含快速 v4，独立快速版必须写明不包含蓄力斩 GP。不要把 RC、pending 或仅静态通过的包标记为正式发布。
