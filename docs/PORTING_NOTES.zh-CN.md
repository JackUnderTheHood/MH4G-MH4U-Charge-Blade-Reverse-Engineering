# MH4G / MH4U 盾斧区域与版本移植说明

本文面向希望把 MH4G Japanese／汉化 v1.2 的最终方案移植到其他区域或版本的研究者。它不是可直接复制的地址表。

## 2. 调试环境前置条件

本项目已验证的研究基线是 **Azahar 2126.0**。此前版本无法稳定维持 GDB 连接，不足以支持长时间动态逆向。准备区域移植前，必须先证明当前模拟器／版本能够稳定完成重复暂停与继续、客体内存读写、小块代码导出、补丁逐字读回和安全恢复；若做不到，应先更换或升级调试环境，不能把连接故障解释为目标版本不存在对应函数或补丁行为阴性。

Azahar 2126.0 是推荐的已知可用基线；其他模拟器版本只有在通过等价稳定性验证后才能替代。此要求针对研究与移植，不自动构成最终 ExeFS 模组的玩家最低版本。

不要把“GDB 可以连接”误解为“可以依赖传统 breakpoint／watchpoint 单步完成移植”。本项目在 2126.0 上仍把交互式断点和监视点视为不可靠的辅助诊断：它们可能产生远程错误、继续失败和高频／同值写入噪声。移植者应优先复用脚本化流程——只读 preflight、可恢复 enable/status/disable、临时代码 hook、有限 logger、内存快照、分块导出与离线分支验证——并让动态行为和最终状态相互验证。

## 3. 不能直接复制 MH4G 地址

JPN v1.2 的最终 hook 为：

```text
00941334  resource overlay
00B0D0A0  native motion wrapper
00CA82EC  no-stick fast entry
00CA830C  stick-input fast entry
00CAC478  action finish wrapper
```

这些是 **JPN v1.2 运行时地址**。其他区域即使 Action ID、函数结构或相对距离相似，也必须重新定位。尤其不能把 `00CA830C` 直接写入 USA/EUR。

移植时应依赖完整指令上下文、调用关系和分支目标，而不是单个四字节签名。单字匹配在大型 ARM 可执行文件中不具备足够唯一性。

## 4. 需要重新确认的语义对象

每个目标版本至少要独立确认：

- 精确游戏版本、Title ID 和代码加载基址；
- 玩家指针根及 Action 读取路径；
- 无摇杆输入快速／普通和摇杆输入快速／普通的 Action 身份；
- 四个同构 morph entry stubs 及其 `(direction, fast)` 参数轴；
- 资源提交入口与原始函数序言；
- native motion 提交调用点；
- 动作结束／恢复调用点；
- 足够大的安全 code cave；
- overlay 内所有外部分支与绝对地址 literal；
- IPS 的运行时地址到文件偏移转换。

现有研究为两组动作编号提供了跨版本线索：不推动左摇杆时使用 `000B/0006`，推动左摇杆时使用 `001C/001B`。移植时仍应通过目标运行时记录，或目标版本自身的入口映射与行为隔离进行等价确认；不能只凭外部金手指资料认定。

## 5. 推荐移植流程

### 阶段 A：只读映射

1. 固定目标 ROM 区域、游戏更新版本、Title ID 和模拟器版本；优先采用已验证的 Azahar 2126.0 调试基线，并确认脚本化内存读写／读回稳定。
2. 在任务地图内确认运行时代码可读，记录代码加载基址。
3. 以小块方式导出可执行代码；若远程 stub 对大块传输有限制，先探测安全块大小。
4. 离线搜索完整函数签名、调用关系和相邻入口结构。
5. 读取四个 morph entry stubs，确认两个参数轴与四种动作一一对应。
6. 扫描候选 code cave，并证明目标范围全零、容量足够且没有已知引用或分支进入。

阶段 A 禁止写客体内存，也不制作发布 IPS。

### 阶段 B：overlay 重定位

1. 以已验证的 640-byte JPN v6 overlay 为行为基线。
2. 保持内部相对分支和 `592/583` literal 的语义不变。
3. 重新编码所有指向目标版本函数的外部分支。
4. 更新目标版本专用的绝对状态或资源地址。
5. 验证每条 ARM B/BL 的源地址、目标地址、链接位与可达范围。
6. 验证镜像恰为 640 bytes，状态区不越界。

不能只做固定地址差值平移；每个外部目标都要由目标版本自身的指令与调用关系证明。

### 阶段 C：离线构建与反向验证

1. 生成候选 overlay 和 IPS。
2. 反向解析 IPS，核对全部记录的偏移、长度和 little-endian payload。
3. 对 overlay、`code.ips` 和 ZIP 生成 SHA-256。
4. 再次解码所有分支并检查目标。
5. 确认构建可重复：连续两次构建应得到一致哈希，或明确记录不可重复元数据来源。

### 阶段 D：可恢复动态候选

1. CPU JIT 关闭，人物在任务地图中完全静止。
2. 运行只读 preflight，要求所有原 hook 和完整 code cave 基线匹配。
3. 先写 overlay、读回签名和初始状态，再最后安装 hooks。
4. 第一轮只做无怪物快速动画 smoke：动画身份、单次播放、自然结束、无崩溃。
5. 再测试普通动画隔离。
6. 最后才进入怪物 GP、红盾瓶爆、派生与连续输入。
7. 动态候选必须有能够恢复原 hook 并清零 cave 的安全路径。

阶段 D 是全新重定位时最稳妥的默认路线。若只是给已经完成动态验收的 overlay 增加最小扩展，也可以用完整重启后、在客体代码被 JIT 编译前自动加载的 ExeFS RC 代替运行中热写；USA v3 的第五 hook 采用了这条路线。此路线仍必须具备目标版本独立映射、原始基线和安装后机器码读回、行为隔离测试、回滚路径以及完整阶段 E 验收。EUR v3 则先采用 CPU JIT 关闭的可恢复动态候选路线，再进入 ExeFS 验收。

### 阶段 E：ExeFS 发布验收

1. 把同一已测试机器码封装为 `code.ips`，不在封装时改变行为。
2. 完全关闭模拟器后安装。
3. 不运行 GDB enable，不读取即时存档，从正常游戏存档干净启动。
4. 只读确认 hooks、overlay、literal 和初始状态由 ExeFS 自动加载。
5. 先完成快速／普通最小 smoke，再进行 CPU JIT 开启的长时间混合回归。
6. 最终状态必须为已知安全状态；发布说明必须记录 Title ID、版本、哈希和即时存档限制。

## 6. 最小回归矩阵

一个同时覆盖无摇杆输入与摇杆输入两种分支的移植版本，至少需要通过：

| 类别 | 必测项 |
| --- | --- |
| 动画 | 无摇杆输入快速、无摇杆输入普通、摇杆输入快速、摇杆输入普通；均单次播放并自然结束 |
| GP | 四个分支的正常防御回归；红盾下观察瓶爆 |
| 连续性 | 至少两次严格连续摇杆输入快速 GP；不得退化或交替 |
| 隔离 | 快速链后普通动作仍保持普通动画与 GP |
| 派生 | X 斧下砸／回旋斩、大解；适用时检查超解 |
| 生命周期 | 动作结束、重复进入、翻滚、收刀、换区与战斗恢复 |
| 加载 | 干净 ExeFS 自动加载，不依赖调试器 |
| JIT | CPU JIT 开启后的实际长测，无卡顿、崩溃或状态污染 |

## 7. 发布门槛

以下任一条件未满足时，只能称为实验候选或 RC：

- 目标版本地址没有独立静态／运行时证明；
- 摇杆输入第五入口只由跨区域地址猜测得到；
- 只验证了机器码读回，没有执行动作；
- 只通过 GDB 注入，没有验证 ExeFS 自动加载；
- 只测试一次 GP，没有普通隔离、连续输入和状态回收；
- 没有校验值、Title ID 或明确的即时存档限制。

## 8. 不属于当前移植范围的事项

把 GP 移植给其他武器不是区域端口，而是新的机制研究。它需要继续拆解 `0x592` 与通用 Guard／碰撞系统的关系，并证明目标武器的动作生命周期能够安全建立和关闭对应防御上下文。现有盾斧 overlay 不能被视为通用模板直接套用。
