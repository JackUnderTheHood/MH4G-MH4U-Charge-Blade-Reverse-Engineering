# 研究历程：从 v3 动作身份方案到 v4 原生 GP 时序

本文不会逐条复述超过一百万字节的 `current_state.md`，只保留真正改变研究方向的节点。更细的候选实验、失败构建和当时的操作步骤仍保存在原始研究档案中；其中引用的原始 `reports/` 属于本地证据集，没有全部放入这套公开文档。

## 1. v3 完成了第一个完整功能闭环

在 v3 阶段，项目已经完成：

- 不推动左摇杆和推动左摇杆的快速变形分支；
- 快速动画、GP、红盾瓶爆和主要派生；
- 普通／快速动作隔离；
- 连续使用和状态回收；
- MH4G JPN／汉化、MH4U USA、MH4U EUR 三地区 ExeFS 发布。

v3 的关键观察是：

```text
普通变形：0x592 → 0x583
原生快速：0x583
```

项目利用五个 hook 和 640-byte overlay，让快速动作在有限生命周期中取得与 `0x592` 相关的逻辑上下文，同时保留 `0x583` 的快速资源。这个组合足以让原有 Guard 和红盾系统产生目标行为。

但 v3 仍有一个没有完全回答的问题：为什么 `0x592` 上下文能够产生完整 GP 和瓶爆，而原生快速 `0x583` 只靠早期状态位实验时只能防御、不能瓶爆？

## 2. 2026-08-13：用严格 A/B 重新打开机制问题

v4 研究没有直接修改已发布的 v3，而是把两个条件放在同一个运行环境中反复切换：

- A：正式 v3，快速动作具有完整 GP 和红盾瓶爆；
- B：保留原生快速动作身份，只用早期实验补入防御相关状态，GP 成立但没有瓶爆。

有效样本按短批次交替采集，并按小／中／大后退分层。旧实验金手指没有正确关闭时得到的混合样本全部作废，没有被纳入结论。

稳定差分说明：A 和 B 都可以完成防御，但瓶爆只在 A 出现。研究由此不再盲猜命中后的大量字段，而是收缩到准备时序、接触身份和成功结果提交之间的有限差异。

## 3. 从高频日志中排除噪音

研究先后建立了多种固定容量日志记录器（logger），只记录少量目标事件，用来观察：

- phase-0 调用顺序；
- motion getter 的调用者；
- 成功接触时的身份与状态；
- 事件分派和原生调用边；
- `state+0x489 bit 2` 的写入与消费。

这一步产生了大量“阴性但有价值”的结果。例如：

- 某些 getter 可以比较 `0x583/0x592`，但实际调用点没有请求 `0x592`；
- 某些函数从能力上可能生成相关副作用，但两次真实红盾瓶爆样本都没有经过对应调用边；
- 修改防御结果或在结果后单独调用候选函数，不能重建瓶爆。

这些结果阻止研究把“函数能做某件事”误写成“这个动作实际依赖它”。

## 4. 逻辑身份 A/B 找到两组关键读取点

项目随后对 motion getter（读取当前 motion 身份的函数）的返回值做可恢复的选择性替换，但不修改内存中真实的 motion。通过逐步缩小调用者范围，研究定位到两组关键读取点：

- 一组调用者需要看到 `0x592`，才能建立完整 GP；
- 另一组调用者需要看到 `0x592`，红盾瓶爆才能成立。

只保留其中一边时，会分别出现“GP 成立但无瓶爆”或“防御本身不成立”的结果；两边同时保留时，完整行为恢复。

这证明动作身份的消费者确实分层，但“从原生 `0x583` 起点，只在两个调用点临时返回 `0x592`”的第一版选择性身份候选仍然失败了：动画正常，却没有 GP。

这条路线随后由两轮有界探针进一步排除：

- **RC1** 只在 `CA7864` 和 `CA8914` 两个已知消费者处尝试把 `0x583` 临时提升为 `0x592`。一次原生快速动作中，探针记录到 2777 次符合基础过滤的 getter 调用，但这两个目标调用点均为 0 次。它们属于流程已经进入 `0x592` 后才出现的下游消费者，不能从原生 `0x583` 起点自行启动这条路线。
- **RC2** 再加入更早的 `AEE784` 身份比较点。该点实际命中 183 次，但 `CA7864`／`CA8914` 仍然为 0，动画虽然正常，GP 依旧没有建立。

因此，失败原因不是简单的分支编码错误，而是“只改 getter 返回值，就能让原生快速动作自行进入完整 `0x592` 生命周期”这个假设本身不成立。研究据此停止继续枚举 getter 调用方，转回真正建立状态的原生 mask 时序。

这个失败很重要。它阻止项目把静态上的对称关系当成已经验证的运行时事实。

## 5. 找到更早、更干净的原生时序

研究回到状态建立的源头，记录 `B56160` 应用 mask 前的 Action、请求 mask 和调用前状态。最终发现原生快速变形本身已经出现可利用的 mask-2 调用。

在严格过滤当前玩家、快速 Action、请求 `mask=2` 且调用前 `F0=1` 后，把本次 mask 扩充成 `0x2012`，可以直接让原生快速动作获得 GP，而不改变 motion identity。

这成为最终 v4 让 GP 防御判定生效的方式。

## 6. 把防御成立和防御性能拆开

早期实验已经知道 `0x10` 与 `0x2000` 同时写入可以得到符合 GP 的防御表现，但两个位的具体消费者尚未闭合。

2026-08-15，项目完成了两个关键因果实验：

1. 在 `B018A8 -> B54EE0` 调用期间临时隐藏 `bit 0x10`。快速 GP 和普通长按防御都只剩火光，无法真正挡住攻击；恢复后两者同时恢复。
2. 静态与运行时核对确认 `B2804C` 消费 `bit 0x2000`，把内部后退判定值减 10（最低为 1），再由 `B0E5B0` 和 `B23B48` 分别选择后退等级与位移。

因此，GP 不再被描述成一个单一 flag，而是：原生动作时序建立防御接受条件，再叠加 GP 的防御性能修正。

## 7. 红盾瓶爆链闭合

研究从 `state+0x489 bit 2` 的写入和消费继续向下追踪，最终连接了：

- 瓶爆对象创建与生命周期；
- 内嵌主动碰撞记录；
- 碰撞列表登记；
- 攻击者／受击者实体解析；
- 命中结果累计与结果队列；
- 目标当前 HP 的最终扣减。

这把“红盾时看见一次爆炸”提升为完整的效果、碰撞和伤害证据链。

## 8. 第一份“v4”重封装被正式撤回

机制闭环后，项目一度把 v3 的五-hook 机器码连同新的 v4 机制文档重新封装，并使用 v4 文件名。用户指出，这不符合 v4 应当具有全新实现的定义。

该包随即被移入历史归档，并明确标记为：

```text
WITHDRAWN_NOT_TRUE_V4
```

它从未被当作真正的 v4 发布。最终 v4 必须采用不同于 v3 的原生时序实现。

这项修正也解释了历史记录中为什么会出现“v4 与 v3 字节相同”和“v4 是两-hook 新实现”两种看似冲突的说法：前者只对应已经撤回的重封装候选，后者才是最终正式 v4。

## 9. 最终快速变形斩 v4

最终快速 v4 使用两个 hook：

- 原生 mask-2 时序上让 GP 防御判定生效；
- 成功快速 GP 接触后的红盾瓶爆条件。

它保留原生 `000B0400`／`001C0400` 动作身份，不修改 motion，不需要 v3 的 640-byte overlay。

日版独立版完成实机验收后，USA 和 EUR 均按各自运行时镜像重新映射地址、人物根槽、分支和 code cave，并分别完成无接触动画、无红盾／红盾 GP、单次瓶爆、派生、普通防御、状态读回和安全恢复。

## 10. 用剑模式蓄力斩做反向验证

用户随后提出把 GP 移植到一个游戏原本没有该功能的动作：剑模式蓄力斩。

logger 确认 `00340400` 蓄力保持阶段具有可利用的同类 mask 时序。第一版只让 GP 防御判定生效，但成功防御后，无论小／中／大后退都会切换到防御反应，导致蓄力中断。后续记录结果动作的观察器证明：

- 小后退对应 substate 3；
- 中后退对应 substate 4；
- 大后退对应 substate 5。

最终补丁会拦住 substate 3／4 对应的小／中后退动作切换，让蓄力继续；substate 5 对应的大后退则保持游戏原本的处理，正常打断蓄力。

瓶爆方面，直接留下 `state+0x489 bit 2` 存在延迟消费风险。最终实现改为在确认蓄力 Action、成功结果和红盾计时后，直接调用目标版本的原生瓶爆提交函数。

这个新动作在三地区都通过测试，证明对 GP 防御判定生效、防御后退和瓶爆链的理解已经能够脱离原快速变形动作复用，是整项研究最强的交叉验证。

## 11. 三地区移植与 EUR 崩溃归因

USA 与 EUR 都先用只读导出和签名定位自己的函数、Action、人物根槽和 code cave，再生成候选。没有使用统一地址偏移，也没有把日版 IPS 改名发布。

EUR 测试中曾两次在爬墙函数 `B96990` 崩溃。初期无法判断是否与候选有关，测试因此停止。后来发现同时启用的一条金手指把 USA 地址 `00B96958` 直接写入 EUR，覆盖了 EUR 爬墙函数的必要指令。

完整冷启动并确认该错误写入消失后，在 GP 候选保持不变的情况下连续爬墙五次稳定，随后完整功能矩阵也通过。因此两次崩溃被归因于错误地区金手指，而不是本项目补丁。这个过程保留在文档中，是因为它展示了如何处理“看起来像补丁崩溃”的混杂因素。

## 12. 2026-08-16：项目正式结项

最终完成六个正式包：三个地区各有快速 v4 独立版和蓄力斩 GP v1 合并版。全部包均由已经实机验收的机器码确定性构建，校验值复算一致。

研究主目标至此关闭。唯一明确保留的测试边界是怪物多段攻击没有专项覆盖；查询 98／99／100 的玩家可见名称也仍未确认，但不影响 GP／后退／瓶爆主链结论。
