# MH4G / MH4U 盾斧逆向研究历程：从单字段猜测到同时覆盖两种输入分支的 ExeFS v3

本文按因果阶段整理研究过程。完整逐轮记录保存在 `../archive/current_state_research_archive.md`；原始未追加结案章的副本为 `../archive/current_state_original.md`。

AI 分析／实现与人工运行测试／数据采集之间的明确分工，见[开发方式与贡献分工说明](DEVELOPMENT_METHODOLOGY.zh-CN.md)。

机制发现阶段发生在 **MH4G v1.2 汉化版** 环境中；后半段时间线还包括 MH4U USA／EUR v1.1 的独立重定位与验收。跨版本复用的是研究逻辑、工具链和实验纪律，而不是 MH4G 地址或补丁文件。

档案中的早期“当前结论”和“下一步”只代表当时现场，不应覆盖本研究历程、公开 README 与 `RELEASE_NOTES.md` 中的当前发布状态。档案顶部追加的收尾章仍用于确认冻结时点的 MH4G 主研究结案，但其中当时记录的 USA／EUR 状态后来已被完成的区域 v3 正式版覆盖。

## 研究成立条件：Azahar 2126.0

本项目不是只靠静态 Listing 就能完成的。动作身份、motion 序列、资源覆盖生命周期、连续重入和安全回收都需要 GDB 运行时证据。此前 Azahar 版本无法稳定连接 GDB，远程调试会话不足以支撑连续采样、补丁读回、对照测试与失败后的可靠恢复。

Azahar 2126.0 提供了本项目首次能够长期依赖的稳定调试基线，使“预检 → 安装 → 读回 → 执行动作 → 状态检查 → 恢复”的闭环成为可重复流程。就研究工程而言，这是项目能够正式立项并最终完成的重要基础设施转折。这里记录的是研究／复现基线；最终 ExeFS 模组本身不要求玩家连接 GDB，不能据此直接推定普通运行的最低 Azahar 版本。

档案中明确切换至 2126.0 的记录发生在 8 月 10 日。本节有意放在逐日时间线之前，因为它是项目完成后确认的复现基线。此前不稳定会话留下了一些有价值的局部观察，但不足以构成可以安全重复、对外发布的传统调试基础。

但 2126.0 带来的主要改善是连接、暂停和内存读写终于足够稳定，并不表示传统 breakpoint／watchpoint 从此可以承担主要逆向工作。实际研究中，断点仍可能以远程 `E01` 或继续失败收场；watchpoint 会在高频状态更新中因同址同值写入反复触发。依靠人工逐步跟踪也无法稳定复现长动作链。因此项目逐步转向自行编写的 GDB 脚本和运行时插桩：用 preflight／enable／status／disable 管理实验生命周期，用临时代码 hook 和有限 logger 记录 motion／Action 序列，用快照与分块导出做离线分析，再由游戏内 GP、瓶爆、动画和派生完成验证。

## 2026-08-03：建立可研究的动作系统地图

研究从约 197 MB、340 万行的 Ghidra Listing 开始。项目建立 SQLite 索引、函数提取、交叉引用、函数比较和 ARM32 分支编解码工具，把最初的大范围搜索收敛到动作创建、Action 分发和运行时字段。

这一阶段确认了：

- `Player+0x11A8` 为当前 Action；
- 无摇杆输入的快速／普通变形为 `000B0400/00060400`；
- `Player+0x28C` 为当前动作帧，`Player+0x234` 可冻结／恢复推进；
- `Player+0xA300` 直接控制红盾量；
- 红盾瓶爆比最终 Action 更适合作为 GP 阳性证据。

第一个局部阳性来自状态字段实验，而不是最终机制。在 `state+0xF0` 中，`0x10` 可以开放防御，单独 `0x2000` 无法防御，两者组成的 `0x2010` 则能表现出符合 GP 的防御性能与后退。快速动作因此可以在保留 Action 和动画时成功防御，但红盾接触仍然没有瓶爆。这证明复制已观察到的防御位只能重建 GP 的一部分，不能重建完整原生路径。

把快速 Action 直接改成普通 Action、复制其他候选字段或跳转到静态上看似对应的 handler，同样没有得到满足全部条件的结果。远程连接不稳定、传统 breakpoint／watchpoint 不可靠以及 JIT 代码缓存共同暴露出明显诊断风险。因此后续以 Azahar 2126.0 为可复现的连接与内存访问基线，但把主要采集路线改为自动化脚本、临时 hook、有限 logger、快照、机器码读回和游戏内因果对照。

## 2026-08-04 至 08-05：排除“命中结果里藏着瓶爆开关”

项目比较普通 GP、快速受击、红盾开关、Guard 结果脚本、事件槽、碰撞对象和多个 transient 字段。重要结果不是找到一个新开关，而是证明：

- 最终 group 5 Action 可能被多段攻击覆盖，不能单独判定 GP；
- 红盾相关状态能解释瓶爆是否显示，却不能给本来没有 GP 的快速动作创造防御窗口；
- 普通与快速在命中结果层的许多候选差分是结果或伴随状态，不是 GP 的根因；
- 不存在一个已经观察到、可在动作中途简单复制过去的常驻 GP flag。

两组特别重要的阴性对照是：把快速防御结果从 `4` 改成普通 GP 的结果 `3`，以及在防御结果后注入盾斧事件 `0x51`。前者只复制了结果 Action 而没有瓶爆，后者同样没有产生瓶爆。干净的红盾开／关快照也没有找到可复制的稳定派生布尔位。这些实验把防御结果处理和可见瓶爆后果，与更早的动作／motion 成因分离开来。

这迫使主线从“命中后发生了什么”回到“动作初始化和 motion 生命周期如何让防御系统进入正确上下文”。

## 2026-08-06：逻辑与动画第一次被拆开

快速活动处理器在 `mode=0` 下首次得到普通动画、GP 和红盾瓶爆。这是关键因果转折：普通逻辑确实能够产生目标防御行为，但直接借用会破坏快速动作外观。

对共同处理器与提交链的追踪说明：`0x592` 作为完整 motion／资源 ID 进入通用提交链，而不是一个局部布尔值。

研究目标由“复制普通 handler”转为“保留普通逻辑身份，同时替换为快速可见资源”。

## 2026-08-07：`0x592`／`0x583` 与首个完整阳性原型

对 motion 资源表、根对象和提交函数的静态与动态分析，确认 `0x592` 与 `0x583` 具有独立资源对象。以 `0x592` 逻辑上下文配合快速资源后，项目首次同时取得：

```text
快速 Action
+ 快速动画
+ 原生 GP
+ 红盾瓶爆
+ 主要派生
```

围绕该原型进行的 phase 与描述符实验进一步证明：

- phase 0 必须持续到防御接触发生时，才能产生 GP；
- phase 1 同时承载可见过渡、音效和派生，不能粗暴删除；
- 同轮或过早提交 phase 1 会使逻辑上下文持续时间不足，GP 随之消失；
- 重复提交、哨兵替换或粗暴删除阶段会造成双动画、缺失过渡、派生损坏或崩溃。

这一阳性原型证明总体方向正确，但全局资源别名会把普通变形也改成快速动画。恢复时机过早还会重新制造双动画。主问题因此变成作用域与生命周期：资源覆盖必须只由快速入口建立，并持续到正确的动作边界。

## 2026-08-08：用 motion 记录代替函数名猜测

低噪音 logger 在共同提交路径记录到：

```text
普通变形：592 → 583
原生快速：583
```

这把快速入口的最小差分从大量共享函数缩小到 motion 身份及其资源生命周期。项目随后定位快速入口与普通入口的尾调用，并开始设计只在快速入口建立、在 motion／动作结束时恢复的 overlay。

本阶段也留下一个通用方法论：玩家眼里的一招并不一定对应一个专用函数；Action、入口参数、motion、资源、碰撞和结果需要分层记录。

## 2026-08-09：从不稳定原型收敛到 v6

多轮 overlay 迭代暴露了三类工程问题：

- 可重入版本出现 SIGSEGV，说明 LR、literal 或恢复边界必须逐字验证；
- marker 残留会让后续普通 `592` 错误使用快速资源；
- 过早按“非 `583` 即清”会把快速动作自身必要的首个 `592` 清掉。

有限 motion 记录得到三组关键前缀：

```text
单次快速：        592 → 583
快速 GP 后派生：  592 → 592 → 583 → 579 → 56B
后续普通：        567 → 592
```

v6 由此引入 A/B/C 前缀状态机：允许快速前缀继续，并利用普通 `567` 在普通 `592` 前回收 dormant marker。严格连续 GP、普通动画隔离、红盾瓶爆、后退、斧下砸、回旋斩、大解和状态回收随后全部通过。

同日，640-byte v6 overlay 被封装为 Azahar ExeFS v2，无摇杆输入四-hook 自动加载和长测完成。

## 2026-08-09：摇杆输入分支解释旧版“偶发失败”

运行时读取发现四个同构入口 `(0,0)/(0,1)/(1,0)/(1,1)`。摇杆输入的快速变形斩 `001C0400` 使用独立 `(1,1)` 入口，完全绕过旧版的无摇杆输入 fast-entry hook。

Action logger 独立捕获到摇杆输入快速路径的 `001C0400`，以及“剑 X→摇杆输入普通变形”路径的 `00040400 → 001B0400`。随后 motion logger 给出受控结构对照：在已安装四-hook 补丁的同一现场，已经被覆盖的无摇杆输入快速阳性对照记录到 `592 → 583`，而尚未打第五 hook 的摇杆输入快速路径在既有 native wrapper 上保持零记录。因此该零结果证明的是分支绕过，而不是 logger 失效。

特别感谢 YouTube 用户 Hazerou。他发布的 MH4U USA Gateshark 资料是帮助项目最初立项的重要外部线索之一，其中还出现了推动左摇杆时使用的快速／普通变形编号 `001C/001B`。该资料用于辅助对比，但不被当作可执行地址证据；MH4G 运行时 logger 随后独立确认了这两个动作身份。

增加 `00CA830C` 第五 hook 后，摇杆输入的快速变形斩保留较远前冲动画，同时稳定取得 GP 与红盾瓶爆。连续三次摇杆输入快速 GP、摇杆输入普通变形隔离、主要派生和状态回收通过。最终 ExeFS v3 由 Azahar 干净启动自动加载，CPU JIT 开启后的长时间实战也通过。

由此，旧版摇杆相关失败的主要解释从“快速动作起手天然没有 GP”修正为“摇杆输入快速分支此前没有被覆盖”。

MH4G 正式包对应 Title ID `000400000011D700`：`MH4G_JPN_v1.2_CB_Fast_Morph_GP_v3_Azahar.zip`。首次封装的 ZIP SHA-256 为 `3D5B864D160497167D2CBD2A3BB6F33128A20A9A6E57CD3940C83387A5BDA941`；其中 `code.ips` 为 698 bytes／6 records，SHA-256 为 `3EB88248D44A9EFE4A83A372A5EA682779BAB2BE8F3E6E8F9101763B88ACA8F4`。

## 2026-08-09：USA 无摇杆输入 v2 验证区域移植方法

MH4G 机制稳定后，项目验证的是移植方法，而不是复制地址。经过校验的 13,627,396-byte USA 运行时导出被用于离线完整签名搜索、分支解码、动作入口结构核对及安全未引用 code cave 选择。由此得到独立重定位的无摇杆输入四-hook ExeFS v2，并完成自动加载与实战验收。它证明行为设计能够迁移，但每个可执行地址、外部分支、绝对状态指针与 IPS 记录仍属于各自版本。

## 2026-08-10：窗口问题收尾

项目一度准备把快速 GP 尾端人工裁剪到指定帧。期间识别出一个重要方法学错误：从动作初始化后的 0 帧直接跳到目标帧会跳过自然 motion／动画事件，可能把已开放的 GP 状态人为保留到很晚。因此，这种直接跳帧得到的晚帧阳性全部撤销为自然窗口证据。

随后通过自然推进的运行时捕获与接触分类，得到保守边界：最晚可信阳性为 `27.0` 帧；最早可信阴性约为 `30.006` 帧，并在约 `30.008` 帧独立复现；28～29 帧仍未分类。既有普通变形参考为 `32.5` 帧阳性、`33.0` 帧阴性。用户还与 MHGU 官方摇杆输入的快速变形斩进行了实际游玩对比。最终确认：

- MHGU 官方摇杆输入的快速变形斩同样具有 GP；
- MHGU 快速 GP 尾端体感与当前 MH4G v3 接近；
- 当前 MH4G v3 的快速 GP 实际窗口比普通变形斩更短。

因此人工裁剪任务正式取消。可以确认快速窗口不是简单完整继承普通窗口；原生生命周期、phase 或 motion 变化自然终止 GP 是强推断，但具体关闭条件尚未定位。

此前“快速起手另有固定原生 GP 空窗”的怀疑也继续降级。旧版可复现失败已经能由摇杆输入分支未覆盖得到更好的解释；本项目没有证明另有一个固定起手空窗。

## 2026-08-10：USA v3 补上此前未覆盖的摇杆输入分支

USA 的四个相邻入口 stub 随后暴露摇杆输入快速入口。第五 hook 被独立编码为 `00CC33B4=EA04A574 → 00DEC98C`；它复用重定位后的 640-byte 行为设计，但没有复用 MH4G IPS 记录或地址。五-hook ExeFS RC1 在 CPU JIT 首次编译客体代码之前通过干净启动自动加载。

约 22 分钟混合回归覆盖无摇杆输入／摇杆输入、普通／快速切换，连续两次摇杆输入快速 GP、连续三次摇杆输入普通 GP、红盾瓶爆、大解、斧下砸／回旋斩、翻滚、换区与战斗恢复。最终五个状态字全零，RC1 逐字节提升为正式 ExeFS v3；目标 Title ID 为 `0004000000126300`，发布包为 `MH4U_USA_v1.1_CB_Fast_Morph_GP_v3_Azahar.zip`：

## 2026-08-10 至 08-11：EUR 排除同址复用并独立完成

Hazerou 的 EUR Gateshark 参考进一步支持相同的游戏层动作编号组合，并提供 EUR 人物根地址，但无法定位可执行 hook。首轮有限只读 probe 明确证明 EUR 不与 USA 共用 hook 地址。因此项目重新导出并校验 EUR 自己的 13,627,396-byte 运行时镜像，独立定位五个 hook 与外部目标，并选择经过单独验证的全零 code cave。

第一次 installer 读回发生在标题画面，而不是任务地图中的静止猎人现场。该结果只保留为安装格式证据，明确不得作为执行或安全证据。测试随后从干净任务地图进程重新开始：CPU JIT 关闭的 GDB 候选通过两条摇杆输入分支、GP、瓶爆、主要派生、连续使用及状态回收，并安全恢复原 hook 和全零 cave；之后 ExeFS RC1 又完成干净自动加载和约 10 分钟 CPU JIT 开启的混合回归，最终五字全零。

已测试 RC1 IPS 原样提升为 EUR 正式 ExeFS v3；目标 Title ID 为 `0004000000126100`，发布包为 `MH4U_EUR_v1.1_CB_Fast_Morph_GP_v3_Azahar.zip`：

## 2026-08-11：主研究正式结案

2026-08-11，项目确认三个同时覆盖无摇杆输入与摇杆输入两种分支的正式版本均已完成：MH4G Japanese／汉化 v1.2、MH4U USA v1.1 与 MH4U EUR v1.1。`0x592` 的通用 GP 机制与其他武器移植转入开放问题，不再作为正式版缺口。

研究主目标至此关闭。`0x592` 与 Guard 的精确因果关系、向其他武器移植 GP 等只保留为 Future Research／Open Questions，不再属于三个正式版的未完成需求。下一阶段是发布工程：按需最终回归、录制对比视频、整理发布包与中英文公开文档。冻结的 `current_state` 文件是研究现场档案，不能直接替代公开 README。

## 主要失败路线及其价值

| 路线 | 结果 | 留下的结论 |
| --- | --- | --- |
| 传统 breakpoint／watchpoint 跟踪 | 远程 `E01`、继续失败或同值写入反复触发 | 主要证据应来自脚本化 hook、有限 logger、读回和游戏内行为对照 |
| 复制单个状态字段／flag | 只有防御而无瓶爆、完全无效、受击或姿态异常 | 没有一个复制位能够重建完整原生 GP 路径 |
| 直接替换 Action／handler | 动画改变但目标行为不完整 | 动作身份、初始化与外部系统存在耦合 |
| 修改 Guard 结果／事件脚本 | 不能创造缺失窗口 | 结果层不是 GP 根因 |
| 粗暴删除或提前提交 phase | 双动画、缺过渡、派生损坏或崩溃 | phase 同时承载视觉与游戏逻辑 |
| 全局 `0x592`／快速资源别名 | 得到 GP，但污染普通动画 | 因果方向正确，作用域错误 |
| 过早清理 marker | 快速动作退化为普通动画 | 恢复必须识别合法 motion 前缀 |
| 直接跳到目标帧测窗口 | 跳过自然事件，阳性失真 | 窗口测量必须让动作自然推进 |
| 假设区域版可执行布局相同 | EUR 在 USA 参考地址上明显不匹配 | 游戏层动作身份相同不代表地址或 IPS 可以复用 |
| 把标题画面安装读回当作运行证据 | 该现场无法执行猎人动作 | 安装格式证据与游戏行为／安全证据必须分开记录 |

失败路线构成了项目最有迁移价值的部分：它们把未来研究者从“寻找一个神奇 GP 函数”引向入口、motion、资源生命周期和 Guard 系统的分层验证。
